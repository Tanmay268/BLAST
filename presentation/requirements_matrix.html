06

Business Dependency Graph — node & edge types

brief, p.5-6; narrowed in context/02_ARCHITECTURE.md (ADR-007)

The brief brainstormed roughly ten possible node types and eighteen possible node attributes. The architecture doc deliberately cut this to four node types, reasoning that the rest were unpopulatable from available data without inventing numbers. Of those four, two were actually built as real graph structures this session.

Node / edge typeBrief suggests itArchitecture scoped itActually built
Service✓✓Yes — real services, 2 systems now
Endpoint / API✓✓Descoped this pass — functional equivalent exists
Datastore / Database✓✓Descoped this pass
Business Capability✓✓As a YAML overlay, not a literal graph node
Message Queue, Cache, Deployment, Team, Infra✓Cut (ADR-007)No real data source — permanently out of scope
Edge: service → service ("calls")✓✓Yes — real edges from trace parent-child spans, 2 systems
Edge: service → datastore, service → endpoint✓✓Descoped this pass
Edge: endpoint → capability ("realises")✓✓A Python dict lookup, not a formal graph edge

Why the simpler version was the right call, not a shortfall: a heterogeneous graph with unpopulated attribute fields (Owner Team, SLA, Revenue Contribution, MTTR — all listed in the brief) would mean inventing numbers RCAEval doesn't provide, which the project's own hard rules explicitly forbid. The graph that got built only contains what could be measured.

Endpoint/Datastore nodes and their edges, reclassified this pass: these were "not done" in the first version of this table, implying they were still on the to-do list. On reflection they aren't — the job a literal Endpoint graph node with a formal realises edge would do (connect an operation to the capability it delivers) is already done by the overlay's realised_by lookup, just as a plain dictionary instead of a graph structure. Formalising that into extra node/edge types would add ceremony without adding anything the pipeline can't already compute. Not building it is a considered call, not a gap.

Priority score formula

brief, p.8

The brief proposes a priority score combining eight factors, with weights possibly learned automatically. The actual formula built is F(S) = Σ w_c · P(capability c impaired | incident set S) — narrower, but every term in it is either measured or an explicitly declared assumption, never invented.

FactorStatusNote
Business ImpactFulfilledDeclared relative weights, w_c, per capability
Technical SeverityFulfilledFolded into p(c|i), from measured statistical significance + effect size
Propagation RiskModeled, empirically inertPresent in the formal model; measured at ~0% on this benchmark (ADR-018)
Dependency CentralityComputed, not used by BLAST itselfPageRank / personalized PageRank exist only as baselines B4/B6
Critical Path ImportanceDescoped this passThe service call graph is shallow (mostly 1-2 hops from any target) — a dedicated critical-path analysis would just reproduce what the centrality baselines (B4/B5/B6/B11/B12, all now built) already show. Not worth a separate computation at this graph size.
Historical Failure ImportanceDescoped this passNo historical incident data exists in RCAEval, and none is plausibly obtainable for this project — building it would mean inventing numbers (hard rule #1). Permanently out of scope, not a to-do item.
Recovery CostDescoped this passSame reasoning — no real repair-duration data exists. Assumed uniform (one engineer, one incident at a time), stated explicitly as a simplification rather than silently defaulted.
SLA Violation RiskDescoped this passNo SLA data available and none plausibly obtainable. A declared "SLA-urgency" alternative VALUE MODEL was built for the sensitivity sweep (§(A6) below) — that is a different, achievable thing from measuring real SLA risk, and is not being conflated with it here.
